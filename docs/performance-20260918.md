# 2026-09-18 部署与性能验证

本次在约 8 GiB 内存、无 Swap 的 Linux / systemd 服务器上验证。AstrBot 为 `v4.28.0-26-gbd046ed29`，Bot 使用 Python 3.12.14，独立后端使用 Python 3.13.5。

这是特定机器和插件组合的一次实测，不是所有部署的性能保证。没有清空页面缓存，也没有控制消息流量与外部服务耗时。

## 启动影响

测量从请求 `systemctl restart astrbot` 到 Dashboard TCP 6185 端口可连接；包括停止旧进程的时间，不等于所有后台任务已经稳定。两组都运行相同外部采集器，避免测量手段差异；此对照衡量增加插件与早期探针的影响，**没有单独隔离外部采集器的因果开销**。

| 测量组 | 第一次 | 第二次 | 第三次 | 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 原始入口，无 MemoryScope 插件和早期探针 | 138.30 s | 131.70 s | 131.49 s | 131.70 s |
| 接入候选版插件与早期探针 | 137.71 s | 137.60 s | 135.84 s | 137.60 s |

这组中位数差为 **+5.91 秒，约 +4.48%**。探针直接记录的工作耗时为 1.13～1.57 秒；不能把剩余差异都当作插件固定成本，其中包含插件加载、调度、后台任务与服务器波动。

之后移除了插件周期清单同步中的模块遍历，补充启动子进程关联与容错。最终版做了一次正常启动复核：**136.91 秒**，比原始组中位数高 5.21 秒；探针记录自身工作约 1.27 秒。这只有一次，不能当成新版的三次中位数。后端最后增加的实验门禁仅在创建实验时执行。

自动 A/B/A 中两次正常加载的“采集器发现启动到端口就绪”分别为 140.67、134.69 秒；这一计时边界和上表不同，不能混在一起算中位数。

## A/B/A 实机验证

目标选择一个普通小插件，B 轮采用 `skip`。每轮端口就绪后等待 60 秒，接着采集 30 秒；每个窗口有 6 个有效样本。

| 批次 | 正常 A1 | 跳过 B | 恢复 A2 |
| --- | ---: | ---: | ---: |
| 服务 anon＋Swap 窗口中位数 | 261.03 MiB | 569.50 MiB | 570.22 MiB |
| 探针记录的加载阶段 | 288 | 285 | 288 |
| 插件报告条目 | 116 | 115 | 116 |
| 目标插件阶段记录 | 3 | 0 | 3 |
| 探针缺失事件 | 0 | 0 | 0 |

最终目标插件已恢复启用，一次性实验计划已清空。三轮记录均完整，启动子进程创建记录各 8 条。后端重启后仍能读取这些记录。

本次 A 组自身就有约 **309.19 MiB** 的波动，远大于小插件可能的收益。计算出的 A−B 为 **−153.88 MiB**，被标记为 `single_trial`（单轮初步结果），**不能据此说目标插件减少或增加了这么多内存**。这次验证证明实验流程和恢复机制可用，不能提供该插件的可靠独占占用。

普通 `disable` 与失败、取消后的恢复路径通过隔离测试验证；实机没有对所有插件逐个执行对照，也没有故意制造生产启动失败。

## 后端常驻开销

最终代码部署后，只重启观察器，让 AstrBot 保持同一 PID，再取相隔 **96.04 秒**的两份快照。期间没有打开报告页反复刷新，Bot 正常运行，采集器保持默认 5 秒采样。

| 指标 | 实测 |
| --- | ---: |
| 后端进程 RSS | 29.16 → 29.30 MiB |
| 后端进程平均 CPU | 单核的 0.29% |
| 后端整个 systemd 服务平均 CPU，含辅助进程 | 单核的 0.52% |
| 新增采样数 | 19 |
| 每次采样平均耗时，含系统调用等待 | 25.44 ms |
| 观察器本次启动以来最慢采样 | 40.40 ms |
| 后端历史数据库及 WAL 等文件 | 13.83 MiB |

CPU 按两次累计 CPU 时间之差除以墙钟时长计算；100% 表示占满一个核心。RSS 含共享库驻留页，不等同于主机新增物理占用。服务 cgroup 物理记账为 18.05～18.31 MiB，内核共享页的记账归属与进程 RSS 不同。

此前连续启动并读取多批报告时，观察器 RSS 最高一次快照约 **52.97 MiB**，所以不能承诺长期始终只有 29 MiB。本次只验证短时常驻开销，不构成长时间无泄漏证明；服务仍设有 192 MiB 内存上限。测量结束时历史丢弃和事件拒绝均为 0，两项服务均 active。

## 使用时的速度与数据边界

- 常态后端每 5 秒读取内核记账，PSS 每 30 秒采样；启动时暂时提高频率。插件只同步清单和代理读取报告。
- 没有开展真实聊天吞吐量或回复延迟的 A/B 压测，因此不能保证回复耗时完全不变。
- 手动对象普查、引用图扫描和 GC 仍在 Bot 内执行，可能造成停顿；连接后端时不会自动周期运行这些扫描。
- 阶段中的异常标志只表示该次调用抛出异常；AstrBot 可能用兼容参数重试成功，需要一起看后续阶段与实际启用状态。
- 配置指纹覆盖 Python 版本、AstrBot 入口、插件元数据及配置文件，不覆盖全部源码、安装依赖、消息流量或外部服务状态。
- 部署保留原 systemd 服务文件并建立专属 drop-in，修改的工具代码已备份；没有删除 AstrBot 业务数据，也没有改持久禁用名单。

## 验证范围

本地完整测试 **188 项通过**。目标服务器核心测试 22 项通过，最后的实验门禁回归 6 项通过（其中 5 项与前者重叠）。浏览器测试覆盖桌面、手机、独立页面及模拟 Dashboard 桥接；没有把模拟桥接测试当作真实 Dashboard 登录后的完整验收。

Python 静态检查、前端 JavaScript 语法检查通过。测试日志中的第三方库弃用提示不属于本次新增故障。
